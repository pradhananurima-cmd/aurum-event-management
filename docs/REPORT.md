## 1. Abstract

AURUM is a static, single-page event management platform for the department's odd-semester
programme. It renders seven events from a JavaScript data source, lets a student filter them by
category, watches a live countdown to the next event, completes a validated three-step
registration and receives a printable pass, and stores the result locally so a student cannot be
registered twice for the same event. Everything is written in HTML5, CSS3 and vanilla JavaScript —
no framework, no bundler, no animation library: seven hand-written files (one HTML, three CSS,
three JS) plus 15 delivered JPEGs (1.7 MB, 4.1 MB counting the 13 original scenes they are cropped from). The code alone
gzips to 38 KB. The interface was designed dark-first with a champagne-gold accent, a high-contrast
Playfair Display voice for display type and a hand-written motion layer.

## 2. Problem statement and objectives

A department runs many events in a semester and the information is normally spread across WhatsApp
forwards, notice-board posters and Google Forms. The assignment asked for a website that keeps the
event data, registration, gallery and contact information in one place. The objectives I set for
myself beyond the minimum were:

1. **Data-driven, not hard-coded.** One array in `js/data.js` feeds the grid, the dropdown, the
   step-2 picker, the countdown, the ticker and the hero statistics. Changing a date changes all of
   them; there is no duplicated markup to keep in sync.
2. **Correct time handling.** Every event is stored as an ISO string with an explicit `+05:30`
   offset and rendered with `timeZone: "Asia/Kolkata"`. Without the second half of that rule a
   9:00 am event displays as “11:30 pm” to anyone opening the page from another timezone — a bug
   worth being able to explain in a viva.
3. **Validation that teaches something.** Regex rules, per-step gating, live re-validation, focus
   management and `aria-live` status text instead of `alert()`.
4. **Motion with restraint.** Signature animation is fine; animation that delays reading is not.
   Every effect is behind `prefers-reduced-motion` and none of them block the first paint.
5. **Zero-dependency deployment.** `git push` → GitHub Pages. Nothing to compile means nothing to
   break between my laptop and the lab machines.

## 3. Design decisions

| Decision | Reasoning |
|---|---|
| Dark-first palette, `#0a0b0f` ink + `#e8c88a` champagne | A high-contrast “award season” look; a light theme is generated by swapping ~30 custom properties in `css/tokens.css`, so both themes share one set of component rules. |
| Playfair Display (display) + Manrope (UI) + JetBrains Mono (data) | A high-contrast serif carries the editorial voice, a grotesque keeps body copy readable, and a mono is used for anything that is a number, a date or a label. Display text is pinned to weight 600 (700 on brand, fees and stats) with a hair of negative tracking, because hairline Didone serifs dissolve at 20 px on a 1x projector. Each stack ends in a generic fallback (`serif`, `system-ui`, `ui-monospace`) so a blocked font CDN still yields a coherent page. |
| Fluid type via `clamp()` | One rule, `--fs-hero: clamp(2.75rem, 8.4vw, 7.4rem)`, replaces three media-query overrides. |
| Cards as data, not decoration | Each event tile carries its own generated artwork, date badge, category tag, fee, seat bar and register action, so the grid is informative rather than ornamental. |
| Photography matched to the event, not decoration | Each event carries its own rendered scene (an `art` field in `js/data.js`) built from the cues a reader uses to name it — dark laptop lab, line-following track, stage and crowd, jury at the display boards, shield on the lecture screen. Nothing is licensed stock imagery, and `tools/make_assets.sh` rebuilds every crop from `assets/src/`. The six gallery frames are separate compositions of the same events — different subject, camera position and crop — and rest under an archive grade, so the 2025 strip never duplicates the 2026 card above it. |
| One Google Fonts request, four weights | `&family=Playfair+Display:ital,wght@0,500..800;1,500..700` plus the two UI faces share a single stylesheet with `preconnect` hints and `display=swap`, so the legibility fix costs no extra round trip and the page is readable before the fonts land. |

## 4. Architecture

```
             ┌────────────── js/data.js ──────────────┐
             │ EVENTS[7] · CATEGORIES · COORDINATORS  │   single source of truth
             └───────┬────────────────────────────┬───
                     │ read                       │ read
        ┌────────────▼───────────┐    ┌───────────▼─────────────┐
        │ js/main.js (features)  │    │ js/effects.js (motion)  │
        │ render · filter · time │    │ rAF ticker · IO · canvas│
        │ wizard · rail · theme  │    │ tilt · cursor · confetti│
        └────────────┬───────────┘    └────────────┬────────────┘
                     │ writes DOM, reads CSS vars  │ reads/writes CSS custom props
             ┌───────▼─────────────────────────────▼────────┐
             │ css/tokens.css (design system) + styles.css  │
             └──────────────────┬───────────────────────────┘
                        localStorage: aurum.theme.v1 · aurum.passes.v1
```

The three scripts are deliberately separated by concern: data never touches the DOM, motion never
touches data, and `main.js` is the only file that writes markup. `effects.js` exposes a small API
(`scrollTo`, `bindTilt`, `burst`, `initMagnetic`, …) which `main.js` calls after it injects new
nodes, so freshly rendered cards get the same treatment as static ones.

## 5. Implementation of the required features

### 5.1 Rendering and filtering
`renderEventGrid()` sorts `EVENTS` chronologically, maps each object to a card template string and
sets `--i` per card for the staggered entrance. The same array fills the registration `<select>`,
the visual picker on step 2, and the `All/Technical/…` count badges.

`filterEvents(category)` uses a **FLIP** pass — record each card's rect, toggle `.is-hidden`,
measure again, apply the inverse delta as a transform, then release it on the next frame — so the
grid reflows with motion instead of snapping:

```js
const before = new Map(cards.map(c => [c, c.getBoundingClientRect()]));
/* …toggle visibility… */
const dx = before.get(c).left - c.getBoundingClientRect().left;
c.style.transform = `translate3d(${dx}px, ${dy}px, 0)`;   // inverted
requestAnimationFrame(() => { c.style.transition = 'transform 560ms …'; c.style.transform = ''; });
```

### 5.2 Countdown and clock
`pickNextEvent()` filters for the first event whose timestamp is still in the future; `updateCountdown()`
decomposes the difference into days/hours/minutes/seconds and `setFlip()` adds a class only when a
value actually changes, so each tile animates once per tick rather than continuously.
`tickClock()` formats `new Date()` with `Intl` for `Asia/Kolkata` and rotates the small dial hand by
`seconds × 6°`. Both run from one `setInterval(…, 1000)`.

### 5.3 Validation
Five rules in one table; each control declares which rule it wants via `data-rule`:

```js
const RULES = {
  name:  { re: /^[A-Za-z][A-Za-z .'-]{1,59}$/,   msg: 'Letters, spaces, dots and apostrophes only…' },
  roll:  { re: /^\d{10}$/,                        msg: 'IEM roll number is exactly 10 digits.' },
  email: { re: /^[^\s@]+@[^\s@]+\.[A-Za-z]{2,}$/, msg: 'Enter a valid email address…' },
  phone: { re: /^[6-9]\d{9}$/,                    msg: 'Enter a valid 10-digit Indian mobile number.' },
  message:{ min: 15,                              msg: 'At least 15 characters, please.' }
};
```

The wizard validates a step before it allows the next one, moves focus to the first invalid control,
re-validates a field as soon as the user starts fixing it, and only renders the review sheet from
data that has already passed. A successful submit generates a pass id (`AUR-1122-U3DG`), stores the
record, bumps the seat counter on that event's card and fires the confetti burst.

### 5.4 Theme
`applyTheme()` sets `data-theme` on `<html>`, updates `<meta name="theme-color">`, writes
`localStorage` and flips the sun/moon glyph. The whole page re-skins from custom properties; the
transition on `background-color`/`color` makes the change feel deliberate instead of abrupt.

### 5.5 Gallery
A `scroll-snap` strip with pointer-drag (click is suppressed past a 6 px threshold and the frame is
remembered from `pointerdown`, because the pointer capture Chrome installs retargets the `click`
event), an arrow pair, a progress meter, per-image parallax clamped inside the frame, and a
lightbox with keyboard, swipe and backdrop dismissal.

**Result of the last run: 72 / 72 passed, no console errors.**

Three real defects were found this way and fixed — worth listing because they are exactly the kind
of bug a viva question targets:

1. `$('#railMeter i')` returned `null` (the `<i>` *is* the element with that id). The throw inside
   the rail's `paint()` aborted `boot()`, so the countdown, the clock and the entire motion engine
   silently never started. Lesson: a single unguarded `null` in a boot sequence kills everything
   after it.
2. While the gallery rail held a pointer capture, Chrome retargeted `click` to the rail itself, so
   `e.target.closest('.frame')` was `null` and the lightbox never opened on desktop. Fixed by
   remembering the frame under the pointer at `pointerdown`.
3. The 4 : 5 gallery images used `transform: scale() translateX()` for parallax; the shift could
   exceed the scale's slack and expose the frame background at the edge. The overhang is now clamped
   and asserted (≥ 8 px at every scroll position).

## 7. Performance and accessibility notes

* No libraries: `js/` is 57 KB raw (data 7.6, effects 16.7, main 33.1) and `css/` 62 KB raw;
  the entire codebase is 37 KB gzipped, so the first paint does not wait on anything.
* Images are lazy-loaded, progressive and same-origin; each gallery frame is its own crop of its
  own source file, so nothing is fetched twice, and the archive-to-colour shift is a CSS filter
  rather than a duplicate copy of each photograph.
* Local stylesheets and scripts carry a `?v=` stamp and `netlify.toml` serves them with
  `must-revalidate` while `/assets/*` stays immutable for a year — a design change therefore lands
  on the reader's next reload instead of after their cache expires.
* Scroll work is done in one shared `requestAnimationFrame` ticker; the grain layer is a single
  tiled SVG data-URI, so there is no per-frame image decode.
* `IntersectionObserver` for reveals and section spy instead of scroll-position maths.
* Semantics: `<header> <nav> <main> <section> <ol> <figure> <address> <footer>`, one `h1`,
  labelled controls, real `<label for>` on every field, `role="status"` on both form messages.
* `min-width: 0` on every grid item — without it a `max-content` marquee inside a `1fr` track
  widened the whole document by 2 253 px on a 390 px phone (found with a per-element
  `scrollWidth` probe, see `tools/`).

## 8. Limitations and future scope

The form validates but does not persist to a server — `localStorage` is a stand-in for the database
the syllabus adds later. The feedback form is client-side only; a Mailgun/Formspree endpoint or a
Google Sheet webhook would make it live. A real deployment would also add an OTP check on the college
email domain, a queue/waitlist when `registered === capacity`, and an admin route to edit `EVENTS`
without redeploying. Since rendering is already data-driven, none of these require touching the UI.

## 9. Conclusion

The assignment's requirements are all present and individually verifiable, and the page is coherent
enough to be used by the department as-is: adding an event is a one-object change, the schedule
stays correct in any timezone, and the registration desk cannot accept a malformed roll number, a
personal email address or a duplicate entry. The engineering value is in the parts that were tested:
the three defects in §6.1 were found by automated checks, not by looking at the page.

## Appendix B — Viva one-liners

* **Why vanilla JS?** No build step to explain, no dependency to break, and the animation is
  measured in 57 KB of logic instead of a 70 KB library doing less.
* **Why `Intl` instead of string maths?** `toLocaleDateString('en-IN', { timeZone: 'Asia/Kolkata' })`
  is the only correct way to print an IST schedule to a viewer who is not in IST.
* **What is FLIP?** First, Last, Invert, Play: measure before, measure after, apply the delta as a
  transform, release it — animation that never triggers layout on the frames in between.
* **Why `data-rule` on inputs?** Validation logic stays in one table; the markup only declares which
  rule applies, so a new field needs no new JS.
* **Where is state kept?** Two `localStorage` keys: `aurum.theme.v1` and `aurum.passes.v1`.
